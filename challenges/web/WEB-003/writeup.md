# WEB-003 Writeup (훈련 후 공개)

**근본원인**: 임무계획 조회 API가 `plan_id`라는 직접 객체 참조만 신뢰하고, 요청자가
그 계획의 소유자인지 **인가 검증을 하지 않았다**(Insecure Direct Object Reference).

**공격**:
1. 본인 팀 계획 ID가 `4000~4004`임을 확인.
2. 그 범위를 넘어 `plan_id`를 순차 스캔하는 스크립트를 작성(수작업 X).
3. `4137`에서 소유자가 `command`인 TOP SECRET 계획이 그대로 열람되며 승인 코드 노출.

**방어**: 리소스 접근마다 소유자/권한을 서버에서 검증(`owner == 요청자`)한다. 예측 가능한
순차 ID 대신 UUID를 쓰면 열거 난이도를 높일 수 있으나, 그것만으로는 IDOR을 못 막는다 —
**핵심은 인가 검증**이다.

**교훈**: "ID를 안다고 접근 권한이 생기지는 않는다." 인증(누구인가)과 인가(무엇을 할 수
있는가)는 다르며, 객체 단위 인가가 빠지면 IDOR이 된다.
